# OBJY website

A Docsify 5 site with a dark theme, centered top navigation, and a chapter menu fixed to the far left. The homepage introduces OBJY with a headline and one large illustration underneath, followed by three illustrated advantages and four use cases in one row. Learn explains Database and Server through a bike and its owner, and Get Started has its own deployment page. Both are linked in the top bar. The hero connects apps, AI agents, and APIs to hundreds of empty object brackets, suggesting a database that scales. The API, JSON object, and memory layers explain the three advantages directly below the hero, with a subtle link to Learn for details. All copy, example data, headings, and destinations are managed in Markdown in English and German. There is no build step.

## Editing

See [the staff editing guide](content/EDITING.md).

All translations are centralized in `content/<language>/`, currently `en` and `de`:

| File in each language folder | Content |
| --- | --- |
| `home.md` | Hero, three illustrated advantages, use cases, images and links |
| `sidebar.md` | Homepage menu labels, destinations, and order |
| `labels.md` | Header links, navigation, controls, metadata, diagram labels |
| `learn.md` | Database and server concepts, illustrated lessons, and code examples |
| `get-started.md` | Getting Started overview and navigation roots |
| `get-started/*.md` | Local server/cluster and cloud setup instructions |
| `documentation.md` | Documentation index and links to individual guides |

Use ordinary Markdown. Preserve Docsify's `:id=...` suffixes across translations. The first standalone hero image appears beneath the headline and introduction. Icon-led bullet lists in the hero become a compact, centered row of highlights, with two columns on smaller screens. Each statement and icon path stays editable in `home.md`. A closing link-only paragraph can become a subtle centered link below that image. Later `##` chapters become full-width detail sections, with illustrated sections alternating text and artwork. Add a link in `sidebar.md` to include a homepage section in the menu. Routine editorial changes require no HTML, CSS, or JavaScript.

`content/languages.json` registers languages and the default. To add a language, copy an existing folder, translate its Markdown files, and add a registry entry. The switcher is built from the registry. See the editing guide for the complete workflow.

The top-bar Documentation link opens the selected language’s `documentation.md` index. It lists DB Server, REST API, and JavaScript client, in that order. DB Server opens `content/server.md`, which loads the main `README.md` from `objy-org/objy`; deployment links use this page too. REST API and JavaScript client use `content/api.md` and `content/client.md`. Server and REST API sources come from `objy-org/objy`; the JavaScript client README comes from `objy-org/objy-client`. Add other guides as Markdown headings and links in each index. Those same entries form a persistent documentation tree: selecting a guide loads it and expands its chapters while the other guide roots remain available. Nested chapters can expand independently, and direct links open their ancestors. Both languages use the same English remote sources; the index and website controls remain localized. Remote Markdown links and images resolve against their source, and linked documents keep the site layout and automatic chapter menus.

## Implementation

`index.html` loads the custom theme in `assets/site/site.css`, the module entry point and document/navigation hooks in `assets/site/site.js`. The theme reads the language registry, selects the requested or saved language, and then loads the pinned Docsify distribution in `assets/vendor/docsify.min.js`. Language selection and URL helpers live in `assets/site/languages.mjs`. The source modules have separate responsibilities:

| Module | Responsibility |
| --- | --- |
| `site.js` | Startup, Docsify hooks, navigation integration, and copy controls |
| `navigation.mjs` | Generated chapter menus and persistent Markdown-driven documentation trees |
| `pages.mjs` | Local/remote loading, relative links/images, and translation fallback |
| `languages.mjs` | Language registry, selection, and language URLs |
| `markup.mjs` | Shared Markdown block grouping, link detection, labels, bindings, and sanitization |
| `homepage.mjs` | Homepage composition, Markdown diagram stories, icon columns, catalogs, and action links |
| `illustrations.mjs` | Shared SVG loading, named symbol fragments, isolated IDs, and accessible image fallback |
| `directories.mjs` | Live Markdown directory indexing, include-source discovery, and unchanged tree-state reuse |
| `documents.mjs` | Markdown guide directories, icon-led setup sections, illustrated guides, and feature catalogs |

Only the homepage module knows about the hero/detail layout. Options are detected from subheadings, and illustrated detail sections alternate automatically. Code examples remain ordinary fenced Markdown blocks with syntax highlighting and copy controls. Link-only lists become actions in the hero and closing section. The homepage's four use cases are ordinary icon-led H3 chapters in `home.md`: AI agents and memory, analytics, application backends, and an open-ended “Or anything else…” option. The options layout detects the number of chapters, up to four columns on desktop, two on tablets, and one on phones. Icons, headings, descriptions, and order stay editable in Markdown. The Features area sits directly below the hero and before the use cases. Three H3 subchapters each contain a short explanation and one standalone image. These form a continuous diagram story: API, JSON objects, then memory. A final link-only paragraph leads to Learn. Headings, descriptions, image paths, order, and destinations remain Markdown content; the renderer does not register particular feature names or a fixed count. A `##` area containing `###` groups and icon-led `####` entries reuses the document catalog renderer, preserving its heading hierarchy, illustrations, descriptions, and IDs. Content is loaded once from the homepage Markdown; there is no catalog include or separate Features page. Deployment options live in each language’s `get-started/` guides, reached through the `get-started.md` overview in the top bar.

Learn lives in each language’s `learn.md` at `#/learn`. Its two H2 chapters are Database and Server. Plain H3 topics cover collections, objects, properties, references, queries, vectors and HNSW, storage, the API, users and permissions, clusters, and persistence. The example consistently uses a bike in `bikes` and its owner Alex in `people`. The left menu is generated from the two chapters and their nested topics. Database and Server use the same 20px navigation icons as Documentation and Get Started; nested topics remain text. Illustrated guides can group H3 topics beneath H2 chapters, mixing images, prose, lists, and fenced examples; each main chapter needs at least one standalone image. Single-level illustrated guides remain supported. The shared guide layout pairs each short explanation with its illustration or code example when the article is wide enough, then stacks them on smaller screens. Diagram compositions also respond to their own column width rather than only the viewport. Optional examples use native Markdown-compatible details/summary blocks below the illustrations, so opening code never squeezes a diagram. Eight SVGs and their labels remain editable through page Markdown and the Learn diagrams table in `labels.md`. The collection hierarchy, resolved reference, physical RAM module, and allowed/denied permission diagram illustrate different concepts rather than repeating code. The permissions lesson adds expandable examples for creating a user, signing in, filtering reads, guarding updates, and changing object rules or collection-wide grants. It explains token renewal and the separate read checks on expanded references.

Docsify renders the Markdown and handles routes. The theme uses the curated `sidebar.md` menu on the homepage and automatically builds other pages’ menus from their rendered headings, including indented subchapters. It arranges homepage HTML into the hero and full-width details, moves the native sidebar into the layout, and binds labels from Markdown tables. The theme supplies the mobile menu and active-section indication. A decorative image with empty alternative text in a Markdown heading becomes a menu icon, removed from the content heading. The same rule works for ordinary guides, illustrated guides, and chapters inside the documentation tree.

The main article is centered in the full viewport with matching left and right gutters. The fixed chapter menu sits outside that space. At 1100px and below, the menu becomes a collapsible drawer. Indexes whose chapters each contain an icon heading, one description, and a destination link become compact clickable directory rows. Link groups remain separate actions in the row. Chapters containing code or starting with a link-only list become setup sections, with link-only lists styled as buttons.

Both Documentation and Getting Started use the same persistent root tree. The localized overview supplies root titles, icons, and Markdown destinations; selecting a guide loads it and generates chapters from its headings while keeping every root available. Clicking the selected root toggles its chapters without changing the article or closing the mobile drawer. A header entry’s directory supplies the tree for its nested routes; this follows Markdown structure without hard-coded page names or entry counts. Directories can link to nested directories: these become indented submenus, with leaf documents loaded only when selected. Returning to a directory collapses its document branches. Each directory revalidates its local Markdown and include wrappers on page navigation, reusing expansion state only while those sources are unchanged. Menu extraction is independent of directory-row styling, so additional descriptive prose does not remove navigation. Nested destinations have separate branch identities, and cycles are guarded. Local include chains identify remote guide sources without downloading unselected remote bodies. Linked remote Markdown carries its Markdown-derived parent in the route, preserving the same roots across chapter links, reloads, new tabs, and language changes. Ordinary Markdown pages still receive a chapter menu.

Getting Started links to `get-started/local.md` and `get-started/cloud.md` in each language folder. Local installs `@objy/cli` once for both One node and Cluster. Cloud is an overview linking to `/get-started/cloud/terraform`, whose localized wrappers include the shared `content/terraform.md` live README reference. Opening Cloud leaves Terraform collapsed and does not fetch the README; selecting Terraform renders it with its chapters indented below that submenu. The overview shows the same icons as its menu roots; guide headings remain plain. Language changes preserve the guide and selected chapter. A standalone `:include` can target a remote URL or a relative local Markdown file; local includes resolve from the wrapper file and reject cycles.

The Features link in the left chapter menu jumps to `feature-highlights`. The three advantages use large, distinct blue, coral, and sage headlines beside the existing API, JSON, and memory artwork. The layers share one source, `architecture.svg`, through `#api`, `#objects`, and `#memory` symbol fragments. Each row pairs its text and image on wide layouts and stacks on narrow ones. The full 21-card catalog is removed from the homepage. Use cases follow the story, with the footer underneath. The curated Markdown menu follows the same order: Overview, Features, Use cases. The four top-bar entries remain unchanged. Generic icon-led catalogs are still supported for Markdown pages that use them.

The first standalone image in each section becomes its illustration. The homepage uses the first symmetric bracket hero, `assets/site/applications-objects-scale.svg`, displayed beneath the headline at up to 1300px. Its orderly field contains 376 empty object brackets on two projected planes, connected to Apps, AI agents, and APIs. The 720 × 480 desktop and 420 × 560 phone layouts share field and endpoint definitions; endpoint labels come from the Application diagram table. The wider asymmetric experiment remains saved unchanged at `assets/site/applications-objects-chaos.svg` (commit `3077520`), and the original layered-object hero remains at `assets/site/applications-objects.svg`. Change the image path and description in both localized `home.md` files to restore either variant. Connection pulses respect reduced-motion preferences. The homepage uses three named symbols from `architecture.svg`: CRUD, query, aggregation, and vector search; one bare task JSON example with nested properties, tags, and a vector; and a physical RAM module with three storage chips. SVG definitions are fetched once, and each fragment includes only its dependencies with isolated IDs. The complete wide and compact compositions remain available in the same SVG. Short diagram labels stay in `labels.md`; the larger explanations stay outside the artwork in `home.md`. An optional Markdown `<details>` block under a story chapter becomes a full-width expandable example below its copy and artwork. The homepage example connects with `@objy/client` to a running server, stores a flexible task object with nested properties, tags, and an embedding, finds it by its status, and adds a nested property to that same object. Its short vectors are illustrative; embedding generation belongs to the application. Referenced illustrations load only when needed and fall back to ordinary images on failure.

Rendered Markdown is sanitized with bundled DOMPurify before it enters the document. Scripts, event handlers, unsafe URLs, styles, forms, and page-supplied translation bindings are removed; headings, code blocks, tables, and details/summary remain available. Local SVG artwork is a trusted repository asset, inlined separately by the shared illustration module.

Fenced code blocks use Docsify's built-in Prism highlighter with a palette matched to the dark theme. Local grammar modules add JSON, Bash/shell, TypeScript, HTTP, YAML, and Markdown to the bundled JavaScript, HTML/XML, CSS, and C-like support. They load before the first page renders, with no runtime CDN dependency. Local and remote documents share the same highlighting. Specify the language after the opening fence, such as `json`, `js`, `ts`, `sh`, or `http`.

Browser metadata updates from the selected language’s `labels.md`; clients that do not execute JavaScript use the fallback tags in `index.html`. Sync those tags when social-preview metadata changes. The neutral loading message, emergency English fallback, no-JavaScript links, and the home logo remain in the shell. Top-menu links highlight the matching page or descendant route with `aria-current="page"`. The Documentation entry is the fallback for guides without their own top-menu link, including live remote documents.

## Local preview

```sh
python3 -m http.server 8000 --bind 127.0.0.1
```

Open `http://127.0.0.1:8000/`. HTTP is required for Docsify to load Markdown. Fonts, artwork, and the homepage engine are all local, with no package installation required.

## Routes

Old `#/features` bookmarks redirect to the homepage Features area, preserving chapter IDs. Sections use standard Docsify hashes with a page-level language parameter: `/?lang=de#/?id=object-capabilities`. The top-bar Get Started link opens `/?lang=de#/get-started`, with cloud and local-server overview rows and collapsible roots. Its guides use `/get-started/local` and `/get-started/cloud`; chapter links include `/get-started/local?id=deploy-cluster` and `/get-started/cloud/terraform?id=hetzner`. The documentation index opens at `/?lang=de#/documentation`. Local setup links open `/content/server?id=run-the-server`; cluster setup opens `/content/server?id=configuration`. Other examples link to REST API chapters such as `/content/api?id=databases`, `bulk-objects`, and `collections`. Existing links without a language parameter use the saved preference or the default language. The explicit URL language wins over the saved preference. Unknown languages use the default. Switching preserves the route and section; preferences remain optional if browser storage is unavailable.

Metadata, the document’s `lang` attribute, controls, alt text, and SVG labels follow the selected language. All document headings keep stable IDs across translations. Code examples and API keys remain unchanged.

Local Markdown links such as `[Documentation](documentation.md)` or `[Setup](guides/setup.md)` open in the same layout. Relative links inside nested documents resolve from that document’s folder. No page registration or separate menu file is needed: use `#` for the title, `##` for chapters, and `###` for subchapters. The top-left logo always returns to the homepage while keeping the selected language.

For a route such as `#/guides/setup`, the site looks for `content/<selected-language>/guides/setup.md`, then the default-language version, then `guides/setup.md` at the repository root. Root-level Markdown and shared files such as `content/EDITING.md` are also supported. Missing pages show a localized message and a home link.

## Content sources

The shared pages load the live main `README.md` and `API.md` from `objy-org/objy`; JavaScript client documentation loads `README.md` from `objy-org/objy-client`. Application examples connect through `@objy/client` or REST to a running server, which owns the in-memory database engine. Keep upstream wording current in those source repositories; the website never rewrites or snapshots their documents.

The database descriptions were checked against the sibling `spread-db` repository (`eb221e0`), particularly `README.md`, `API.md`, and the storage implementation. The `objy-db-installer` README describes deployment and planned resize/restore workflows. Getting Started references the live `objy-org/terraform` README through `content/terraform.md`. All externally maintained documentation is referenced, with no checked-in copies or snapshot fallback. The source must be publicly readable; private sources show the standard unavailable message. Remote content is fetched with cache revalidation when opened or reloaded, so no website build is needed after source edits. GitHub raw-content caching can delay visibility. No GitHub credentials are sent to visitors.

Compression is in memory; the local write-ahead log and S3 journals/snapshots provide persistence. Replication is asynchronous. Topology changes are planned maintenance. Optional object behavior extensions are distinguished from the database core. Recheck those distinctions when updating product claims.
